# 规划你的首次接入

从一个高风险操作入手，明确一组前置检查项，并让执行工具在动手前先核验裁决。同一套评估契约，能把策略定义、证据采集与执行拦截无缝串起来。

## 选择可观测的操作入口

| 起步场景 | 核心检查项 | 推荐入口 |
| --- | --- | --- |
| 文件清理 | 目标文件校验、仅限临时文件、单批数量上限 | [可选：不用模型运行文件清理](getting-started.zh-CN.md#可选不用模型运行文件清理) |
| 应用发布卡点 | 目标应用与环境、必需的测试或健康观测指标 | [跑一遍首批检查](getting-started.zh-CN.md#跑一遍首批检查)与[交付集成指南](integrations.zh-CN.md) |
| 配置或数据变更 | 预期资源范围、业务规则要求的前置观测指标 | [GuardrailSpec 字段参考](guardrailspec-reference.zh-CN.md)与 [HTTP API](api.zh-CN.md) |

首次接入时，优先选择“工具方便采集观测数据、执行端也便于复核证据”的操作场景。

## 明确三方职责分工

1. **策略维护方：** 发布 GuardrailSpec，并指定 Scene 当前生效的策略版本。
2. **Agent 或评估器：** 读取冻结后的策略要求，执行前置检查，并使用该 Run 的专属提交凭据上报完整结论与证据。
3. **执行工具：** 在真正动手前读取权威 Run 记录，核验上下文、裁决有效期、已采信证据及当前目标状态，再结合自身权限决定是否放行。

OpenGuardrail 负责按策略校验证据并落库裁决，观测采集与最终执行控制则由集成方对接真实系统。读取和重试逻辑详见 [Run 与 Submission](runs.zh-CN.md)。

## 选择部署方式

| 使用场景 | 存储与部署建议 |
| --- | --- |
| 本地体验与验证 | 使用原生二进制或源码构建，通过 SQLite 启动服务，或直接运行一次性文件清理 Demo。 |
| 团队共享与审计留存 | 配置 PostgreSQL 存储，保持每个数据库对应一个服务实例。 |
| 远程接入与生产托管 | 将服务置于可信 HTTPS 代理之后，并配置好管理员与机器凭据。 |

具体配置参见[配置与存储](configuration.zh-CN.md)、[Docker 部署](docker.zh-CN.md)与[管理员初始化](local-administrator.zh-CN.md)。

## 跑通一次完整闭环

先跑通本地示例，对照查看“被拦截（DENY）”和“放行（ALLOW）”两次评估，并在控制台里看清被采信的原始证据；随后再把示例策略与观测源替换成你自己的业务操作即可。

当前处于开发预览阶段，HTTP API 版本为 `v1alpha1`。请采用文档说明的单实例部署架构，并在升级版本时留意核对 API 契约。

下一步请继续阅读[快速开始](getting-started.zh-CN.md)。
